# 豆包签到请求样本与「参数是否拼错」判定

> 用途：回答「我们模拟的请求数据是不是有问题、导致签不上」这类反复出现的疑问，
> 并把真机抓到的真实请求留档，作为以后对照的基准。
> 证据来源全部是真机抓包，不是推断。

## 1. 结论先行

1. **我们的签到不发请求**。适配器做两件事：活动页上下文 fetch `detail`（只读）
   + CDP 点「立即签到」按钮。点下去之后的 `checkin` 请求是**客户端自己发的**，
   签名（`msToken` / `a_bogus`）由页面 JS 生成，连接器没有拼装面。
2. **唯一我们自己拼的请求是 `detail`**，实测 `code=0` 正常受理。
   2026-11-19 真机对照：我们拼 `version_code=23610`，页面自己发 `version_code=20800`，
   两者返回**逐字段一致**（`checked_in_today` / `continuous_days` / `tasks` / `progress` 全同）。
   即：少带的那十几个参数不影响读路径判定。
3. **「签到失败请稍后重试」= `710010702`，不是参数缺项**。同一次点击里
   客户端自己发的 `checkin` 也返回 702，而同会话 `detail` 仍 `code=0`
   ——读路径正常、写路径失败，指向账号级服务侧状态，不是我们拼错了。
4. 702 的定性在 2026-11-17 已收敛（三条证据：同机另一账号成功 / 异机同账号同败 /
   卸载重装不复位）——**账号级服务侧写路径故障，本地无可修项**；处置是停点等自愈，
   或用手机端同账号旁证。2026-11-19 Leisure520 手动点击成功，说明该账号已自愈。

## 2. 真实签到请求（`POST /alice/ug/campaign/landing/checkin`）

抓包时间：2026-11-17，Windows，豆包 2.36.8，账户 `doubao_cn:main`，
点击坐标 `(548,378)` / `(817,255)`，共 4 次点击，其中 2 次捕获到请求。

| 项 | 真实值 |
|---|---|
| method / path | `POST /alice/ug/campaign/landing/checkin` |
| body | `{"scene":"pc_incentive_task_mvp_v3"}` |
| query（客户端自带） | `version_code=20800`、`language=zh`、`device_platform=web`、`doubao_device_platform=web`、`aid=497858`、`real_aid=497858`、`pkg_type=release_version`、`device_id=`（空）、`pc_version=2.36.8`、`doubao_pc_version=5.74.99`、`web_id=<19位>`、`tea_uuid=<16位>`、`region=`、`sys_region=`、`samantha_web=1`、`web_platform=desktop`、`use-olympus-account=1`、`web_tab_id=<uuid>`、`runtime_version=5.74.99`、`runtime=web`、`msToken=<168位>`、`a_bogus=<188位>` |
| response | HTTP 200 `{"data":null,"code":710010702,"msg":"系统错误","error":{"code":710010702,...}}` |

对照：`detail` 用**同一会话**、参数少十几个，仍然 `code=0` 满数据返回。
→ 「参数不齐导致签不上」这条假设在真机上不成立。

## 3. 我们能自己拼的那部分（仅 `detail`，只读）

```
GET /alice/ug/campaign/v3/detail/?version_code=<运行时派生>&language=zh
  &device_platform=web&doubao_device_platform=web&aid=497858&real_aid=497858
  &pkg_type=release_version
body: {"campaign_group_code":"pc_incentive_task_mvp_v3"}
```

`version_code` 运行时从客户端安装版本派生（写死会在客户端升级后回 702）。
2026-11-19 实测 `23610` 与服务端页面自发 `20800` 返回一致，无需改常量。

## 4. 怎么再取一次样本（按需，不要常开）

现成机制：`DOUBAO_REQUEST_CAPTURE=1` 时，适配器在点击前装只读页面旁路，
点击后把 `checkin` / `detail` 请求（method / url / query / headers / body /
response，敏感值已脱敏）追加写入：

```
~/.butler/doubao_requests/doubao_requests-YYYY-MM-DD.jsonl
```

**默认保持关闭**（2026-11-17 裁决）：页面 fetch/XHR 猴补在字节反爬页面的生产 run
里禁用，取证改用 CDP Network 域旁听。所以这条只在「专门取证」时临时打开：

```powershell
$env:DOUBAO_REQUEST_CAPTURE = "1"
# 跑一次未签账户的领取，取样后立刻关掉并重启服务
```

已知局限：页面旁路只能看到 JS 可见的 URL，脚本注入早于页面拦截器时
`msToken`/`a_bogus` 可能缺失；要拿全量签名参数得用 CDP `Network.enable` 旁听。

## 5. 判读口诀

- `code=0` + `checked_in_today=false` → 确实没签，点按钮
- 点击后复查仍 `false`，且台账 4 秒内返回 → 先看有没有抓到 `checkin` 请求：
  - 抓到 + `710010702` → 账号级服务侧写路径故障（停点等自愈，勿连续点）
  - 没抓到 → 点击没落到按钮上（坐标/遮挡问题，属实现缺陷，可修）
- `710012001` → 登录过期（NO_AUTH），走人工重登
- `2` → 活动换季，更新 `CAMPAIGN_GROUP_CODE`

2026-11-18 `doubao_cn:Leisure520` 两次失败（13:39 切号后、17:49 已是活跃态）
当时 capture 关闭、无样本，故两种原因无法区分——这也是本文档要保留样本的原因。
