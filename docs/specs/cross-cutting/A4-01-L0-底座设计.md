# A4-01 · L0 底座设计

> 凭据保险库 / 账号健康中心 / 事件总线与通知 / 审计。M0 交付，
> 是 L1~L7 全部能力的安全地基。

## 1. 凭据保险库（Vault）

**分层存储**（优先级从高到低）：

| 层 | 实现 | 适用 |
|---|---|---|
| OS Keychain | macOS Keychain / Windows Credential Manager（DPAPI） | 官方 Connector 凭据 |
| 加密库 | AES-GCM，主密钥来自 Keychain（Keychain 不可用时回退口令派生） | 无法进 Keychain 的文件型凭据（cookie 库等） |
| 内存 | 进程生命周期 | 运行时解密产物，绝不落盘 |

API（core 端口）：

```
vault.store(account_id, kind, secret)      # 加密入库 + 记录轮换历史
vault.load(account_id, kinds) -> Secret[]  # 按 Connector 申报的最小集合解密注入
vault.rotate(account_id, kind, new)        # 换新 + 旧值进历史（可审计）
vault.health() -> [CredentialHealth]       # 有效期/状态，喂给健康中心
```

规则：
- **最小授权**：`load` 只解密调用方申报的 kinds（A2-02 §5）
- 凭据明文只存在于内存与 Keychain；日志/事件/台账里一律 `[REDACTED]`（继承旧系统脱敏机制）
- 到期监控：每日 job 比对有效期，产出 CREDENTIAL_EXPIRING / EXPIRED 事件

## 2. 账号健康中心

```
AccountHealth = {level, evidence, checked_at}
level: healthy | expiring | expired | invalid | risk
```

- 探测器 = 特殊的 Run（kind=health.check），走 Connector 的 status 探测声明
- 分级驱动 UI：healthy 静默；expiring 徽标提醒；expired/invalid 进"待处理"
  并带 repair_hint（"重新打开客户端登录" / "打开登录页"）
- 封号风险信号（连续 NO_AUTH、异常错误码簇）→ level=risk，severity=push 通知

## 3. 事件总线 + 通知中心

```
EventBus（进程内 asyncio）
  ├─ subscribers: 台账写入 / 统计聚合 / 通知中心 / 规则引擎(L3)
  └─ 事件 schema: {type, ts, account_id?, severity, payload}
```

通知渠道（适配器，可插拔）：

| 渠道 | 默认 | 说明 |
|---|---|---|
| 应用内 | on | 待处理列表 + 托盘角标 |
| 系统通知 | on（仅 attention 级） | 全部成功 = silent，零打扰 |
| Webhook | off | 通用出站 POST（飞书/钉钉/Server酱经配置模板适配） |
| 邮件 | off | 每日摘要形态，不做逐条推送 |

规则：
- 通知中心是 Event 的**唯一消费者出口**；其他订阅者不许直接通知
- severity: silent / badge / push 三级，用户可在设置里按事件类型覆盖
- 通知必须可追溯到 Run/Event id（点击通知 → 对应证据页）

## 4. 审计（Audit）

- append-only 表：`{ts, actor, account_id, credential_ref(哈希非明文), action, outcome}`
- 触发点：凭据存取/轮换、所有写操作（claim/import/route 变更）、连接器安装与升级
- 反代上线（R4）前审计必须就位——这是 L3 的安全底线，不是可选件
- 提供导出（JSON）用于排障；保留策略默认 90 天

## 5. 数据层约定

- SQLite(WAL) 单库；表按域分置（现状：accounts / runs / audit / health_state /
  vault_items / vault_history——凭据元数据与健康态同库；events 走进程内总线不落库，
  `usage_samples` 时序表 R2 落地）
- `usage_samples` 独立时序表、按天分区（量级远大于业务表），不混业务查询
- 台账写入失败 → 事件总线记 error 并降级重试，**不影响业务主流程**（继承旧系统 ingest 语义）
- Repository 接口隔离：SQL 只存在于 packages/engine 适配器层（kabao_engine）
- **schema 演进**（2026-11-12 增补）：新表 = `CREATE TABLE IF NOT EXISTS` 落本域
  适配器（现状纪律不变）；**加列/改列 = 必须配套显式迁移**——启动时按
  `PRAGMA user_version` 顺序执行迁移语句（随首个真实迁移落地机制，此前禁止
  假设空库直接改列：单机产品老用户的存量库不会自己升级）
- **数据根**（2026-11-11 补，M0 遗留修正；2026-11-12 R1 更名 kabao）：库统一落平台标准
  用户数据目录 `kabao/`——macOS `~/Library/Application Support`、Windows `%APPDATA%`、
  Linux `$XDG_DATA_HOME`；`KABAO_DB` 环境变量整体覆盖（测试/便携模式）。
  **禁止 CWD 相对默认**——否则运行数据混进代码仓库（曾发生）；旧品牌目录
  `ai-marina/marina.db` 与 CWD 旧库首次运行自动迁入数据根（`bridge.default_db_path()`，
  迁移源优先级与幂等性见 A1-03 §8）
