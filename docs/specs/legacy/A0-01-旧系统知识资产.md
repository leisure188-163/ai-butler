# A0-01 · 旧系统知识资产清单（非移植）

> **定性：auto-signin-kit 不是代码来源，是协议字典 + 行为验收基准。**
> 前代项目的每个 Connector 都从本仓库的领域模型出发**全新实现**；
> 旧项目只回答两个问题：「接口长什么样」（协议）和「正确行为是什么」（验收 oracle）。
> 任何把旧代码文件搬进新仓库的动作都是架构事故，code review 直接打回。

## 1. 为什么不能搬

旧架构已暴露的弊端，正是新项目存在的理由：

| 旧弊端 | 新系统的对应解法（搬家会原样带走这些病） |
|---|---|
| `domain/域` 为中心，用户被迫理解架构术语 | Account/Provider 为中心，域概念下沉为实现细节 |
| 同一能力三种入口（`qoder auto` / `client_signin run` / `doubao auto`） | 统一 Action/Run 模型 |
| 批处理骨架硬撑常驻服务（反代/采集无安身处） | 网关独立进程 + server 常驻的进程模型 |
| 结果语义散落各层（needs_attention 有记录无出口） | core 结果枚举单源 + 事件总线 |
| 声明式引擎只能声明"签到"一种能力 | Connector 能力矩阵声明 |
| 命令行为主入口，界面是事后加的 | 界面为主入口，CLI 降级为执行器 |

## 2. 允许带走的（只有三种，且形态全部重做）

### 2.1 协议知识 → `packages/connectors/src/butler_connectors/<id>/PROTOCOL.md`（重写为版本化文档）
- 各家端点、请求头、信封/加密格式（旧仓库协议笔记已归纳：Qoder 风控头/COSY、
  Trae SS_AES、豆包 Cookie/CDP、WorkBuddy 成长中心接口族）
- 业务码语义与幂等性结论（哪些接口重试安全、哪些写操作不可重试）
- 凭据解锁协议（密钥位置、解密流程）——知识带走，实现按新引擎重写

### 2.2 行为基准 → 验收对照表（不带走任何代码）
每个 Connector 新实现完成后，与旧系统对同一真实账号跑一次：
同样的输入 → 领取结果、幂等行为、错误分类必须一致。旧系统从此退役为 oracle。

### 2.3 教训 → 本文件 §1 的表（已记）

### 2.4 历史数据（运行数据，2026-11-15 增补）
「禁搬代码」不禁**迁用户数据**：旧 kit 产生的签到流水/账户档案属于用户资产，
经一次性导入脚本（`scripts/import_legacy_kit.py`，干跑默认 + 备份 + 幂等 +
行数验证 + 源只读）并入 butler 台账；词汇映射逐词核对（旧 RESULT_LABELS 与
新 Status 同源），无诚实对应的词一律 status=NULL + 原文档案入
`params_json.legacy_kit`，不发明语义。

## 3. 明确不许带走的

- 域三件套骨架、entry_points 注册机制、polydomain-cli 结构
- CLI 子命令形态与参数布局
- 旧的 store/report/调度代码文件
- 任何 `*.py` 整文件复制（含"改改名字"式的复制）

## 4. 实现顺序（由简到繁验证底座，不是迁移顺序）

1. trae_cn（纯声明式 HTTP）→ 2. qoder_cn（声明式 + 设备风控头）→
3. doubao_cn（CDP 编排）→ 4. workbuddy_cn（签到最小集，ADR-008 收敛）

**M1 硬标准**：每个 Connector 不加特殊分支接入新模型；
若某个必须写例外 → 停下来改模型，不是改代码。

## 5. 旧仓库处置

旧仓库已打 `v1-maintenance` tag 冻结（只修 bug 不加能力）；协议结论转写进各
Connector 的 PROTOCOL.md 后，文档角色由新仓库接管。
