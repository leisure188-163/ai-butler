# A1-04 · 网页会话通道与跨平台矩阵

> R3 开篇 v1（2026-11-12）。两个承重裁决已批：**捕获机制 = 直读浏览器 cookie**、
> **首批矩阵 = Chrome · mac+Win 双平台一等公民**。
> 本文只写战略面：通道定位、跨平台矩阵、第一批边界；实现细案（凭据 kind 细节、
> 探针形状、逐家取证记录）随批次落 A2-03 与各连接器 PROTOCOL。

## 1. 为什么需要网页会话通道（R3 定位）

- 产品定位 = 本地优先的 AI 账号管家，市场性要求「不装桌面客户端也能用」。
- 现有 4 家客户端连接器的接入矩阵是「每 app × 每系统」：每加一家产品、每补一个
  平台都要一条真机取证链（M1 只取证了 Windows，trae 是唯一 mac 全链先例）——
  矩阵发散，不可持续。
- 网页会话把矩阵收敛为「每浏览器 × 每系统」：ChatGPT / Claude / Gemini /
  Trae 网页版 / Qoder 网页版全吃同一条通道，**加产品 ≈ 零增量取证**。
- 词表依据：A1-03 §3「导入」定义本就是「从本机客户端/**浏览器**读取凭据建立
  账号」——网页捕获不是新词，是「导入」的第二证据源；A1-01 §里程碑 R3 行锚点。

## 2. 双通道定位（已裁）

| | 网页会话通道（R3 起，**广度主通道**） | 客户端 dock 通道（M1 起，深度面） |
|---|---|---|
| 覆盖 | 浏览器处处有，与装没装客户端无关 | 要求本机装对应客户端 |
| 数据深度 | 取证后定（以会话可见数据为限） | 深（trae 29 包 / workbuddy 85 包分账本、入账流水） |
| 凭据耐用性 | cookie 滚动过期 + 风控挑战 | 设备绑定 token 更耐用 |
| 平台成本 | 每浏览器 × 每系统（收敛） | 每 app × 每系统（发散） |
| 接入动作 | 导入 + 体检 + 到期提醒 | 导入 + 领取 + 采集 + 体检 |

分工纪律：

- **新家数默认走网页通道**；客户端连接器不扩张，除非数据深度有决定性增量。
- 已接入 4 家不动；它们的 mac 分支按「mac 装机量 × 数据增量」排优先级、按需取证，
  不承诺全量（workbuddy 若 mac 无客户端则不接）。
- 同一家产品两通道并存时是**两个凭据源**，各成各卡，不自动合并。

## 3. 捕获机制（已裁：直读 cookie）

**直读 Chromium 系浏览器本地 cookie 存储，Chrome 起步**；浏览器扩展通道留作
备选、不进首批。

- 为什么不是扩展：扩展 = 一个新端（新工程面 + 安装摩擦）；直读与 dock 取证
  「读本机已有状态」同构，贴合本地优先。
- 代价（显式接受）：mac 首次读取要过一次 Keychain 授权（Chrome Safe Storage）
  ——导入流程文案必须交代这一步；用户拒绝授权 = 导入失败如实报（红线 5），
  不静默、不降级。
- ❌ 禁止：cookie 明文落盘（进 vault 加密信封）；对浏览器的任何写操作（只读）。

## 4. 跨平台矩阵（已裁：Chrome · mac+Win）

| 浏览器 \ 系统 | Windows | macOS | Linux |
|---|---|---|---|
| **Chrome**（首批） | DPAPI 解 Chromium cookie key——unlock.py 已有，**复用** | Keychain「Chrome Safe Storage」——**已取证（2026-11-12 本机 M1，见下）** | 后排不排期 |
| Edge / Brave / Arc | 同 Chromium 解锁链，后排（增量小） | 同左 | — |
| Safari | — | cookie 沙盒保护，取证成本高，后排 | — |

- 平台策略：Windows / macOS 双平台一等公民（市场通用性要求）；Linux 不排期。
- 矩阵每格 = 一条「解锁链」取证，与具体 app 无关——这就是 §1 收敛的兑现。
- 客户端连接器的 mac 分支不进本矩阵（per-app 取证，归 §2 分工）。

### 4.1 mac Chrome 解锁链取证记录（2026-11-12，M1 真机只读）

环境：macOS 24.3.0 / Chrome 157.0.8103.39（运行中）/ login.keychain-db。

1. **钥匙面**：Keychain 条目 service = `Chrome Safe Storage`、acct = `Chrome`；
   `security find-generic-password -w -s "Chrome Safe Storage"` 读出 24 字节密钥
   （管道内存态，不落盘）。**首次读取弹 Keychain 授权框**——用户拒绝 = 导入失败
   如实报（§3 代价条款的实证）。
2. **库面**：`~/Library/Application Support/Google/Chrome/<profile>/Cookies`
   为 SQLite；Chrome 运行中持锁 → **拷贝件只读**（密文拷贝，用后即删）。
3. **解密链**：encrypted_value 去 `v10` 前缀 → PBKDF2-HMAC-SHA1（密钥，
   salt = `saltysalt`，**1003 轮**，16 字节）→ **AES-128-CBC** → PKCS7 去垫。
   **密文体双形状**（2026-11-13 真机取证修正，见下）：
   - 经典形状（Chromium 旧文档口径）：体 = 密文，IV = 16 个空格；
   - 前缀形状（本机 Chrome 157 全量实证）：体 = **16B 未定论段 + 16B 真 IV + 密文**。
   两种形状的补位都可能有效（CBC 链尾数学一致），只有明文可 UTF-8 能区分——
   unlock.py 按双形状自识别（先经典后前缀，选 PKCS7 有效且 UTF-8 可解码者）。
4. **验证口径修正**（2026-11-13）：前次「528/528 全解零失败」只验证了
   解密不抛异常（补位有效 ≠ 明文可读）——经典形状下 528/528 补位全有效，
   但明文非 UTF-8。复验后：358/358 按前缀形状解出可读明文（CBC 链数学：
   整体按空格 IV 解密时第 2 块起全对 ⇒ IV = 体[16:32]）。一把钥匙覆盖全部
   profile（per-installation）不变。
8. **结构定论（2026-11-14 真机闭环，推翻 4 的「未定论」）**：mac v10 密文
   实为**单条 CBC 链**——
   `体 = E(IV=16空格, sha256(host_key)[:32] ‖ PKCS7(cookie_value))`：
   - 「16B 未定论段」= 链首块（加密 sha256(host) 前半）；「16B 真 IV」=
     链第二块（加密后半）——它天然可作后续块的 CBC IV，这正是前缀切法
     「也能解」的数学原因，两种切法从未是两种形状
   - 前缀切法输出 = 跳过 32B 头的载荷 = cookie 真值——现行 unlock.py
     一直返回正确值
   - 「与明文确定性相关」系误读：seg 与 **host_key 一一对应**（91 host =
     91 seg，跨 profile 恒定 19/19）；同值跨 host → 不同 seg（29 组反例）
   - **完整性验证闭环**：经典整链解密头 32B == sha256(host_key)（528/528），
     整链重放 E(sp, sha256(host)‖载荷) == body（528/528）——头不符 =
     显式事故（钥匙错/库形状变），capture 层落地校验
   5. **expires_utc** 为 WebKit 纪元（1601-01-01 起微秒），换算后与 cookie 真实
   有效期一致。
6. **本机实证的两种导入语义**（天然试金石）：ChatGPT 会话令牌在库但已过有效期
   （「cookie 在但过期」→ 应如实出过期卡）；Claude 两 profile 均无会话 cookie
   （「未登录」→ 如实报未登录，不是错误）。
7. `security` CLI 形态可行（ADR-008 helper.js 子进程同构先例）；API 注入
   （Security.framework）留作 A2-03 细案选项，测试隔离照 DPAPI 适配器先例走
   api_factory。

## 5. 凭据与语义（领域面预告，细案归 A2-03）

- 新凭据 kind：`browser_cookie`——一次导入 = 一个 cookie 集凭据对象，
  关键 cookie 各自 expiry 取最早者为凭据有效期。
- 失效语义：体检探针 403 / 挑战页 → `NO_AUTH` + repair_hint「重新导入」
  （协议七词不发明新状态，两层词汇原则照旧，见 conventions/3）。
- vault 存储不动（加密信封 + 同步审计）；端零映射照旧（探针结论 = core 出产
  字面量 + signal）。
- kind 收敛原则（A2-02 §3）照旧：网页捕获 = 新 capture 通道 + 新凭据 kind，
  一套运行时，绝不 per-app 平行代码。

## 6. 第一批范围（R3 = ChatGPT + Claude）

- 能力：**导入**（session 入包）+ **体检**（会话有效性探针）+ **到期提醒**。
- 用量可见性：取证后定——探针能看到什么就接什么，不发明、不承诺。
- ❌ 首批不做：自动领取（这两家无对应概念，不发明）、会话迁移（R5）、
  对话代理（R4 后）、多浏览器铺量（按矩阵后排节奏走）。
- 风控边界：只读探针 + 导入读取；challenge 类 cookie（cf_clearance 等）如实
  存储不伪造——遇风控如实 `NO_AUTH`，不做对抗性绕过。

## 7. 取证纪律（沿用 M1 先例）

- 只读取证、最小头一次只读、遇 403/风控页即停、token/cookie 不落盘、
  evidence 不含明文凭据。
- 新增浏览器侧纪律：先在浏览器开发者工具**手动确认** cookie 名单与判活端点，
  再写连接器代码（同四家连接器 PROTOCOL §7「先取证后实现」先例）。
