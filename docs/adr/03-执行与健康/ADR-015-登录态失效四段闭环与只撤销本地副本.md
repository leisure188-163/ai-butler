# ADR-015 · 登录态失效走四段闭环，失效凭据只撤销本地副本

- **状态**：Accepted
- **日期**：2026-11-16
- **决策者**：butler 维护者
- **关联**：A2-02 §4（声明式鉴权码）、A2-07 §5（健康分级与修复）、A2-08 §2（调度闸门）、
  A4-01 §2/§3（严重度与通知渠道）、A3-01 §3（待办修复入口）、ADR-007 决策 8（会话级切号
  自动化；登录不自动化）

## 背景

qoder 真机签到返回 `HTTP 401`，但被记成 `FAILED`，形成一条完整的静默链：

1. **归类断线**：声明式运行时把传输层错误一律归 `FAILED`；
2. **可见断线**：`FAILED` 的 `is_attention=False`，`/pending` 只聚合 attention 结果，
   仪表盘待办永远看不到它；
3. **可修断线**：传输错误分支不带 `repair_hint`，用户即使看到也不知道怎么修；
4. **重复断线**：`CheckinSchedule` 没有健康闸门，每个班次照打，上游持续 401。

用户感知是"一直在失败，也不知道什么情况"，而系统侧没有任何一处主动说"这是登录态失效，
需要你重新登录"。

**否决的方案**：登录态失效后自动清空会话数据、强制客户端重新登录。

- 桌面四家（trae/qoder/workbuddy/doubao）的登录态在**客户端自己的存储**里，butler 清自己的
  库既不能强制客户端登出，也不能触发重登，只会丢掉证据与历史；
- 网页两家（chatgpt_web/claude_web）的 cookie 副本可以"失效即作废"，但它必须是**用户显式
  修复动作的一部分**，不能由调度器在后台静默清库；
- 登录本身按 ADR-007 决策 8 **不自动化**（扫码/手机号需人工参与）；账户间会话切换已自动化，
  但**登录态失效后的重登仍人工**——切号只能在已登录会话间进行，救不了过期会话。

真机抓取结论（2026-11-16）：Qoder 点「退出登录」后日志只有 `[Auth] User signed out` +
`[AuthStore] Credential storage diagnostic {"operation":"clear"}`，没有任何 `logout/signout`
远程请求；Trae CN / 豆包客户端未找到可复用的 logout HTTP 接口；ChatGPT / Claude 网页端有
next-auth 会话，远程 signout 会同时吊销用户浏览器共享的会话，副作用不可接受。因此
"自动调用远程退出接口"在桌面端不成立；butler 能做且应该做的，是**在判定登录态失效后撤销
自己库里的凭据副本**，让后续 Run 不再拿旧 token 反复打上游，同时保留归档与审计证据。

## 决策

**四段闭环：归类 → 可见 → 可修 → 熔断；失效凭据只撤销管家本地副本。**

### 1. 归类（A2-02 §4）

- `TransportError` 携带 `status_code`（仅 HTTP 非 2xx）；
- `AuthSpec.reauth_status_codes` 由连接器显式申报，默认空 = 不申报；
- 命中申报码 → `NO_AUTH` + 证据「鉴权被拒（HTTP xxx）——登录态已失效」+
  `RepairHint(action_id="relogin")`；未申报的 4xx/5xx 仍 `FAILED`，不替连接器猜 HTTP 语义；
- trae_cn / qoder_cn 申报 `[401, 403]`。

### 2. 可见（A2-07 §5、A4-01 §2/§3）

- `expired` / `invalid` 的严重度由 `BADGE` 升为 `PUSH`；`risk` 保持 `PUSH`；
- 每次动作落地（`POST /runs`、`claim-all`、调度触发）后立即评估健康，级别变化发
  `ACCOUNT_HEALTH_CHANGED`；
- 新增系统通知渠道 `SystemChannel`（min_severity=PUSH）：macOS 用 `osascript`、Linux 有
  `notify-send` 则用；其它平台**如实抛错**，由通知中心隔离记日志，不假装送达；
  本期未实现 Windows toast：`SystemChannel` 在 Windows 显式失败并记日志，桌面壳接入时替换
  runner（不是静默降级）；
- server 默认开启（`BUTLER_SYSTEM_NOTIFY=1`），测试/CLI/引擎库默认关闭。

### 3. 可修（A3-01 §3）

- `/pending` 原样带出 `repair_reason` 与 `repair_action_id`；
- 待办行给「重新登录 / 重新扫描」入口；展开后是两步人工引导：
  「1. 打开客户端完成登录 → 2. 点『我已登录，立即重试』」；
- 重试复用 `POST /runs`（带 `account_id`），按真实结果如实转述成败；
- `relogin` 重试必须先重新停靠（dock）读取客户端新凭据，再发 `POST /runs`。前端
  `repairAccount` 的顺序固定为 `POST /platforms/{target}/import` → `POST /runs(account_id)`；
  导入未发现该账户时如实提示，不空跑重试。

### 4. 熔断（A2-08 §2）

- `CheckinSchedule` 注入 `assess_health`；触发前若级别为 `invalid` / `expired` / `risk` 则跳过，
  不再按班次反复打上游；
- 同一 `(target, account, window)` 只记一条 info 日志，不刷屏；
- **手动重试不受闸门限制**（用户修完后必须能立刻恢复），成功后健康评估回到 `healthy`，
  下一班次自动恢复。

### 5. 失效凭据只撤销本地副本

- **端口**：`VaultPort.revoke(account_id, *, reason) -> int`。
  - 撤销该账户全部槽位的当前凭据：旧值先归档到 `{account_id}:{kind}@{slot}#{seq}`
    （`vault_history` 留痕、后端仍可找回），再删除主引用；
  - `vault_item` 行保留并写 `revoked_at` / `revoked_reason`（可审计、可展示），不物理删行；
  - 幂等：已撤销行跳过；后端主引用已缺失也继续标记；
  - `load` 命中已撤销条目 → `CredentialRevoked`（继承 `CredentialMissing`，连接器仍按
    NO_AUTH 处理，不会静默给空凭据）；
  - 重新 `store` 同 `(account_id, kind, slot)` 清空撤销标记、刷新 `rotated_at`，恢复可用；
    `CredentialHealth.stored_at` 供健康评估区分新旧凭据时代。
- **触发**：`AssessAccountHealth` 在「存在 NO_AUTH 连败（含由此判出的 `invalid/risk`）或凭据
  已过期（`expired`）」时自动调用 `revoke`。
  - 只看鉴权失败事实，不按最终级别误伤：`risk` 若来自其它信号不触发；
  - **连败只算最近一次 `store`（重新停靠/轮换）之后的失败**：新凭据不能被旧凭据时代的
    NO_AUTH 连坐；全部副本已撤销时健康至少为 `invalid`，不得报 healthy；
  - 只在健康级别落定时触发，不在连接器执行层逐次清；
  - 撤销失败不掩盖健康结论，证据里如实写失败原因；事件 `ACCOUNT_HEALTH_CHANGED` 仍按级别
    变化发一次。
- **边界**：只动 butler 自己的保险库。**不调用任何远程 signout、不删除客户端凭据文件、不强制
  客户端登出**；桌面端"退出登录"仍由用户在客户端完成。
- **可见**：`/api/v1/accounts` 的 `CredentialOut` 带 `revoked / revoked_at / revoked_reason`；
  UI 标「本地副本已撤销，等待重新停靠」，待办引导写明「客户端退出并重新登录 → 点重试
  （会先重新读取本机凭据）」。

## 后果

**正面**：

- 登录态失效从"静默失败"变成"待办里的一条 + 一次系统通知 + 一个重试按钮"；
- 失效账户不再消耗每个班次的无效请求，日志只留一条原因；
- 失效凭据不再被后续 Run 反复使用，401 噪音和无效上游请求收敛；
- 旧值归档 + 审计 + revoked 标记，证据不丢；撤销范围严格限制在 butler 库内；
- 修复路径从"点重试但仍旧 token"变成"先重新导入新凭据再重试"；
- 归类、严重度、通知、熔断、撤销各自单点可测（连接器/引擎/server 三层新用例覆盖）。

**负面/约束**：

- 失效判定依赖连接器**显式申报**鉴权码；新接入应用漏申报就仍会记 `FAILED`（有意的显式
  契约，需在接入清单里检查）；
- 健康事件只在级别**变化**时发：用户忽略首条通知后不会反复弹窗，但待办仍在；
- 修复的最后一步（在客户端重新登录）必须由用户完成，butler 无法代劳；
- 系统通知依赖平台命令（`osascript` / `notify-send`），无命令的 headless 环境只留日志与
  应用内待办；
- 撤销后该账户在重新停靠前不可执行任何需要凭据的动作（有意的硬失效）；自动撤销是健康评估
  的副作用，打开账户页也可能触发一次（幂等，有审计）；
- `vault_item` 保留撤销行后，健康评估必须跳过 revoked 行，否则会把已撤销凭据的有效期继续
  算成 expired。
