# ADR-031 · 平台名单列归属用户、编码不可变

- **状态**：Accepted
- **日期**：2026-11-19
- **决策者**：用户（本轮明确要求「合并成一个 platform_name，这个名称允许用户修改
  …… 平台编码写入后就不能修改的」）
- **关联**：ADR-018（平台册表名）/ ADR-034（账户别名）/ ADR-003（多账户）

## 背景

平台册原本有两个名字列（真机核对 2026-11-19）：

| 列 | 谁写 | 表现 |
|---|---|---|
| `platform_name` | 连接器 `manifest.display`，经启动同步与 `reload_connectors` 热重载写入；旧 `upsert` 的 `ON CONFLICT` 带 `platform_name=excluded.platform_name` | **每次同步都覆盖** |
| `name_override` | 只由 `PATCH /platforms/{id}` → `update_profile` 写入，同步不碰 | 只在用户改过时非空 |

显示派生 `display = name_override or platform_name`。库内实测：五条
`platform_name`（AgentRouter / Doubao CN / Qoder / Trae CN / WorkBuddy CN），
三条 `name_override` 非空（三家的「国内版」后缀）。

两个列的问题不是冗余本身，而是**语义分叉**：

- 用户把平台改成「Trae 主号」，改的是 `name_override`；下一次连接器升级把
  `manifest.display` 改了，底层 `platform_name` 变，界面看起来没变——但任何
  绕过 `display` 派生、直接读 `platform_name` 的新代码都会读到连接器的名字。
- 两列并存时，"用户到底认哪个名字"要靠 `or` 猜。新增读端每写一遍派生，
  就多一个漏掉派生、只读 `platform_name` 的机会。

用户裁决：**只留一列 `platform_name`，它归用户；`platform_code` 是锚点，写入即不可改。**

## 决策

1. **数据层只留一列**：`plat_platform` 删除 `name_override`；`PlatformEntry` 删除
   `name_override` 字段，保留 `platform_name`（非空校验不变）。
2. **写入时机**：接入同步（`SyncPlatforms` → `upsert`）只在该平台**首次插入**时写入
   `platform_name`；`ON CONFLICT` 分支不再更新它——连接器后续改名不影响用户看到的名字。
3. **改名入口**：`PATCH /api/v1/platforms/{platform_code}` body `{"platform_name": "..."}`。
   - 长度 ≤ 40（与账户别名同口径）；空串 = 恢复连接器申报名（服务端从
     `manifest.display` 取回，取不到则 400 显式报错）；
   - 404 平台不存在、400 过长，显式报错不静默兜底（红线 5）。
4. **编码不可变**：`platform_code` 没有任何改写入口（端口只有 `update_profile` /
   `set_schedule_override`，都不碰 code）。它是 `acc_account.platform_code`、
   `exe_claim`、调度表、run target 的连接锚点——改它等于迁移多张表。
5. **"是不是默认名"不落库**：`PlatformOut.name_is_default` 在请求时与
   `registry.get(code).manifest.display` 现比一次；连接器已下线（取不到 manifest）
   按「非默认」处理，避免误报可恢复。不新增第二份名字。
6. **老库迁移**：`SqlitePlatformRepository.__init__` 在补列前先执行
   `UPDATE plat_platform SET platform_name = name_override WHERE TRIM(name_override) <> ''`，
   再丢弃该列；随后 `_reorder_columns` 因列序不符触发整表重建，把多余列丢掉。
   缺列兜底值改为按 DDL 默认取（`_DDL_DEFAULTS`）——`capabilities` 这类
   `NOT NULL` 列落 `NULL` 会直接炸。
7. **运行期回填入口**：`POST /api/v1/platforms/resync`（界面按钮「同步平台」）——
   重扫连接器把 manifest 事实写回名册、重排调度，返回同步后的名册。

   为什么必须有：名册此前只在**后端启动**与**连接器热重载**时自动同步，运行期
   没有任何入口。实测（空库、后端不重启）：`GET /platforms` = 0 条；
   「接入全部」候选来自名册，所以**返回空数组、一个也不接**；单家「接入」能跑通
   （它只看连接器是否登记）但**名册仍是 0 条**，留下「有账户、没平台」的悬空态。
   于是用户「清空平台表后点同步平台 → 再点接入账户」的两步式路径无从实现。

   端点语义与启动同步完全一致（共用 `sync_platform_facts`，不复刻第二套）：
   新连接器首插落名、已存在行不被覆盖、已下线连接器落 deprecated 不删行。
   回填后平台的 `client_version` 取不到就用启动期那份端口（`app.state.provisions`），
   避免重建 adapter。

## 后果

**正面**：

- 一个名字一个来源：界面、导出、日志都读 `platform_name`，不会再出现
  「显示一套、库内一套」
- 用户改名永久生效——连接器升级、热重载、重启都不覆盖
- **平台册可自助重建**：清空表、连接器升级后点「同步平台」即可，不必重启后端；
  「同步平台 → 接入账户」两步分离，名册与账户各自有明确入口
- `platform_code` 作为锚点被显式锁死，后续账户 / 凭据 / 调度引用不会被改名打断

**负面/约束**：

- 连接器申报名在界面上不再单独可见（`name_is_default` 只告诉「是否默认」，
  不告诉默认名是什么）。要看原名只能点「恢复默认名」看回填结果
- 首次插入时若 `manifest.display` 缺失，`platform_name` 会退化成 `platform_code`
- 升级补丁若改了 manifest 名，用户已改过名的平台不会跟着变——这是刻意的
