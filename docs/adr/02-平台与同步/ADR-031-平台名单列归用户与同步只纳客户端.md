# ADR-031 · 平台名单列归用户，同步只纳本机客户端

- **状态**：Accepted
- **日期**：2026-11-19
- **决策者**：用户（本轮明确要求「合并成一个 platform_name，这个名称允许用户修改……
  平台编码写入后就不能修改的」；「同步平台时 web 端的不要导入，只导入客户端的应用，
  还有在界面上做一个功能，还有哪些没有导入，让用户手动去导入」）
- **关联**：ADR-001（platforms 为第六业务域）/ ADR-003（账户显示层与人工后缀）/ A2-09（platforms 域 spec）

## 背景

### 两列平台名导致的语义分叉

平台册原有两个名字列（真机核对 2026-11-19）：

| 列 | 谁写 | 表现 |
|---|---|---|
| `platform_name` | 连接器 `manifest.display`，经启动同步与 `reload_connectors` 热重载写入；旧 `upsert` 的 `ON CONFLICT` 带 `platform_name=excluded.platform_name` | **每次同步都覆盖** |
| `name_override` | 只由 `PATCH /platforms/{id}` → `update_profile` 写入，同步不碰 | 只在用户改过时非空 |

显示派生 `display = name_override or platform_name`。库内实测：五条 `platform_name`
（AgentRouter / Doubao CN / Qoder / Trae CN / WorkBuddy CN），三条 `name_override` 非空。

问题不是冗余本身，而是**语义分叉**：用户把平台改成「Trae 主号」，改的是 `name_override`；
下一次连接器升级把 `manifest.display` 改了，底层 `platform_name` 变，界面看起来没变——但任何
绕过派生、直接读 `platform_name` 的新代码都会读到连接器的名字。两列并存时"用户到底认哪个
名字"要靠 `or` 猜，新增读端每写一遍派生就多一个漏掉派生的机会。

### 网页版占位名册

启动同步与「同步平台」端点原来把**所有未退役连接器**都写进 `plat_platform`：本机客户端
（`kind=client`）与网页版（`kind=web`）一视同仁。平台页因此出现用户根本不用的网页版平台
（如 AgentRouter），名册被非本机应用占位；而网页版没有本机客户端可探测，版本/图标恒为空，
看起来像"坏了一半"的平台。用户要的是名册等于「我这台机器上能用的应用」，网页版属于**可选**。

此外名册此前只在**后端启动**与**连接器热重载**时自动同步，运行期没有任何入口：空库不重启时
`GET /platforms` = 0 条，「接入全部」候选来自名册所以返回空数组，留下「有账户、没平台」的
悬空态——用户「清空平台表后点同步平台 → 再点接入账户」的两步式路径无从实现。

## 决策

### 1. 数据层只留一列 platform_name

- `plat_platform` 删除 `name_override`；`PlatformEntry` 删除 `name_override` 字段，
  保留 `platform_name`（非空校验不变）。
- 写入时机：接入同步（`SyncPlatforms` → `upsert`）只在该平台**首次插入**时写入
  `platform_name`；`ON CONFLICT` 分支不再更新它——连接器后续改名不影响用户看到的名字。
- 改名入口：`PATCH /api/v1/platforms/{platform_code}` body `{"platform_name": "..."}`。
  长度 ≤ 40（与账户别名同口径）；空串 = 恢复连接器申报名（服务端从 `manifest.display` 取回，
  取不到则 400 显式报错）；404 平台不存在、400 过长，显式报错不静默兜底（红线 5）。
- `PlatformOut.name_is_default` 在请求时与 `registry.get(code).manifest.display` 现比一次；
  连接器已下线（取不到 manifest）按「非默认」处理，避免误报可恢复。不新增第二份名字。

### 2. platform_code 写入即不可改

- `platform_code` 没有任何改写入口（端口只有 `update_profile` / `set_schedule_override`，
  都不碰 code）。它是 `acc_account.platform_code`、`exe_claim`、调度表、run target 的连接
  锚点——改它等于迁移多张表。

### 3. 自动同步只纳本机客户端与用户自建平台

- 自动同步（启动 / 热重载 / `POST /platforms/resync`）只纳两类：
  `manifest.kind == "client"` 的本机客户端；用户自建平台（`manifest.root_dir` 非空，
  创建即入册，不退回清单）。
- **内置网页版不自动纳册**：出现在平台页「未导入的平台（N）」区块，按行提供
  「＋ 导入 xxx」按钮，点击 = 纳册 + 立即接入（`POST /platforms/{target}/adopt`）。
- **策略性跳过 ≠ 退役**：`SyncPlatforms.execute(facts, known_codes=universe)` 的
  `known_codes` 传「未退役连接器 id 全集」；`deprecate_missing` 只把真正从连接器宇宙消失的
  行落 deprecated，否则每轮同步都会把网页版误标退役。
- **未导入判据**（`GET /platforms/unimported`）：连接器存在且未退役、名册里没有活跃行；
  `account_ids` 如实带上名册外的既有账户（>0 = 导入后自动归位）。
- **导入复用同一投影**：`adopt` 与同步共用 `platform_fact`，不另拼一套字段；未知/已退役
  连接器 422，不静默吞。

### 4. 运行期回填入口

`POST /api/v1/platforms/resync`（界面按钮「同步平台」）：重扫连接器把 manifest 事实写回名册、
重排调度，返回同步后的名册。端点语义与启动同步完全一致（共用 `sync_platform_facts`，
不复刻第二套）：新连接器首插落名、已存在行不被覆盖、已下线连接器落 deprecated 不删行。
回填后平台的 `client_version` 取不到就用启动期那份端口（`app.state.provisions`），
避免重建 adapter。

### 5. 老库由迁移链收编

合并列与重建表已 squash 进 `db/migrations/001_initial.sql`（`plat_platform` 现 12 列、
无 `name_override`）；适配器零 DDL、零自迁移，存量库靠 baseline 列集校验认账。

## 后果

**正面**：

- 一个名字一个来源：界面、导出、日志都读 `platform_name`，不会再出现「显示一套、库内一套」
- 用户改名永久生效——连接器升级、热重载、重启都不覆盖
- 平台册可自助重建：清空表、连接器升级后点「同步平台」即可，不必重启后端；
  「同步平台 → 接入账户」两步分离，名册与账户各自有明确入口
- `platform_code` 作为锚点被显式锁死，账户 / 凭据 / 调度引用不会被改名打断
- 名册只剩本机应用；未导入是显式、可操作的清单，不再是"看不见的差异"

**负面/约束**：

- 连接器申报名在界面上不再单独可见（`name_is_default` 只告诉「是否默认」，不告诉默认名是
  什么）；要看原名只能点「恢复默认名」看回填结果
- 首次插入时若 `manifest.display` 缺失，`platform_name` 会退化成 `platform_code`
- 升级补丁若改了 manifest 名，用户已改过名的平台不会跟着变——这是刻意的
- 网页版若用户从未点导入，其既有账户仍保留在账户域，只是平台不在名册；未导入清单会提示
  「名册外已有 N 个账户待归位」
- `sync_platforms` 用例多一个 `known_codes` 参数（可选，缺省 = facts 集合，保持老语义）

## 备选（未采纳）

- **只按 `kind` 过滤，不带连接器宇宙**：会把网页版每轮同步都误标 deprecated，
  历史行反复"退役又复活"，审计噪声大。
- **网页版完全不可导入**：用户偶尔要用网页版连接器（如 AgentRouter 签到），一刀切等于砍能力。
- **在 manifest 上加"是否自动纳册"开关**：每个连接器都要维护，且用户无法感知；
  由端按 `kind + 自定义` 统一裁决更简单。
