# ADR-001 · 出站适配器独立成包，core 按六业务域分包

- **状态**：Accepted
- **日期**：2026-11-10（2026-11-14 六域分包、2026-11-17 platforms 独立为第六域）
- **决策者**：hiclaw520 + AI（经业界标准查证后裁决）
- **关联**：A1-02 §2/§5、A1-05、A4-01 §5、02-开发红线 §1.3（core 纯净）、cross-platform-arch hexagonal-arch.md R1-R9

## 背景

A1-02 §2 分层图画了 `engines/`（出站适配器：HTTP / 凭据解锁 / CDP / SQLite / 调度器），
但 §5 目录规划和脚手架都没有给这个层落点——实现第一步就会撞上：Keychain(Vault)、
SQLite 仓储、事件总线落地、调度器这些适配器**需要被 server 与 CLI 共享**（两端都直调 core）。

候选方案：

| 方案 | 内容 | 问题 |
|---|---|---|
| A | 独立包 `packages/engine` + bridge.py（skill 规约正形） | 模板里没有，需新建 |
| B | 独立包但无 bridge，端直接 import 适配器 | verify 六边形门禁继续失效 |
| C | 端内适配器 | Keychain 等要在两端复制；只适用小 demo |

约束与依据：

1. **业界标准（COLA 4.0）**：四层 = 适配器层 / 应用层 / 领域层 / **基础设施层**。
   基础设施层承载持久化、外部服务、RPC 等技术细节，通过**依赖倒置**实现领域层定义的端口；
   start 层（组合根）负责装配。hexagonal-arch.md §1 给出同构对照：
   `infrastructure → packages/engine`、`start → apps/server 组合根 / bridge 工厂`。
2. **仲裁约定**：遇争议以 cross-platform-arch skill 为准；skill 正形即方案 A
   （R1 纯净 / R2 方向 / R4 唯一出桥 / R6 用例层编排唯一入口）。
3. **门禁现状**：`verify_project.py.check_hexagonal` 写死 `packages/engine/src`，
   不建该包则"六边形桥闭合"检查静默跳过。现为**九项门禁**（`--test` 时十项，见 AGENTS.md）。
4. **红线 3**：core 零框架依赖 → keyring 等第三方库进不了 core，适配器必须在外层。

core 内部分包方式同样决定业务边界是否可见：若按技术概念横切（实体集中一个目录、
端口集中一个文件），改一个业务的对外面要动全库公共端口文件，跨域耦合无从拦截。
分包单位必须与业务单位一致——**目录即业务地图**。

## 决策

### 1. 出站适配器独立成 `packages/engine`（包名 `butler_engine`）

1. 依赖方向恒定：`端 → core`、`engine → core`；engine 不依赖任何端。
2. `butler_engine/bridge.py` 是端触达引擎的**唯一出桥**：装配适配器 → 构造用例 →
   把引擎原始输出经 core 领域词汇归一后返回。
3. 适配器按**能力**分子包（`vault/` `ledger/` `scheduling/` `http/`…），禁止用旧业务目录名（R3）。
4. `core/bootstrap.py` 保留为纯装配根（只认端口协议）；bridge 调它并传具体适配器。
5. server / CLI 统一 `from butler_engine.bridge import ...`。

**排除项**：`packages/connectors/`（Connector 包）**不属于** engine——Connector 是被
core 端口调度的领域扩展，不是基础设施适配器（见 A2-02 §1）；`apps/gateway` 也不是 engine
的一部分，仅通过 IPC/HTTP 与主控通信。

### 2. core 按六业务域分包 + shared 内核

1. **目录即业务**：`butler_core` 内按业务域分包——`shared / accounts / platforms /
   execution / usage / health / scheduling`（六业务域 + shared），每域固定三件套
   `domain.py + ports.py + usecases/`；端口随域走，不设全库单一 `ports.py`。
   `butler_engine` 对齐同一域图。
2. **依赖恒等式**：域间依赖只允许 `域 → shared`，禁止域互依；跨域编排由用例组合完成
   （用例可以跨域读，域的 `domain.py` 不得 import 其他域）。依赖方向入门禁机检。
3. **platforms 是独立第六域**：平台（连接器家族）被多域引用——账户名册挂
   `platform_code`、调度按平台排班、执行按平台路由端口，寄居账户域会造成引用倒挂。
   故 core = `butler_core/platforms/`（`PlatformEntry` + `PlatformRepository` +
   `SyncPlatforms`），engine = `butler_engine/platforms/sqlite.py`，表 `plat_platform`。
   其它域只持 `platform_code` 字符串，不 import 本域；`/platforms` 契约与路由不变。
4. **命名统一 butler**：包名 / CLI / env / db / 存储键按 A1-03 §6 映射总表。
5. **历史兼容收口在装配期**：旧数据源迁移集中在迁移链与 `butler_engine/db/migrate.py`
   一次性完成（幂等、旧文件保留不删、写审计），运行时零 legacy 分支。
6. **裁决回收是红线**（conventions/01 第 8 条）：ADR 合入时必须同步回收受影响 spec，
   文档漂移在 review / 门禁层拦截。

## 后果

**正面**：

- 与 COLA/skill 标准同构，server / CLI / 桌面 sidecar 共享同一批适配器，无端间复制
- 门禁原样生效（无需改门禁代码），九项门禁齐整；换实现只动 engine，core 与端零改动
- 目录即业务地图：看目录就知道业务边界；端口随域走，改一个域的对外面只触碰该域
- 依赖恒等式机检后，跨域耦合无法静默滋生

**负面/约束**：

- 多一个包与 bridge 装配纪律；端绕过 bridge 直 import 会被 verify 拦截（属预期）
- bridge 装配发生在 engine → engine 依赖 core，注意不要反向（`check_dep_direction` 兜底）
- 本决策豁免流程走 R9：后续任何"端直连适配器"的需求须先记 DESIGN-DECISIONS 再实施
- 域间禁止互依 → 跨域功能必须经用例组合；shared 只放真正跨域的原语
