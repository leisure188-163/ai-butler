# ADR-012 · core/engine 按业务域分包并从零重写，多账号模型并入

- **状态**：Accepted
- **日期**：2026-11-14
- **决策者**：hiclaw520 + AI（brainstorm 六问逐项裁决）
- **关联**：落地 [ADR-010](ADR-010-一人多账号领域模型方向.md)（状态由 Proposed 转 Accepted）；
  延续 [ADR-011](ADR-011-Butler更名与品类句退役.md)（butler 工程标识映射总表）；
  改写 [A1-02](../specs/architecture/A1-02-一核多端落地.md)、
  [A2-01](../specs/domain/A2-01-领域模型与动作模型.md)；
  新建 [A1-05 总设计](../specs/architecture/A1-05-按业务域重写总设计.md)
  与 A2-11..A2-15 五册业务域 spec；[conventions/02](../conventions/02-开发红线.md)
  增补第 8 条红线（裁决回收）

## 背景

系统经多轮重构仍未满足预期。2026-11-14 全面盘点结论：

1. **core 未按业务域分包**：`kabao_core/domain/` 是按技术概念横切的实体仓库
   （account/action/run/event/schedule/usage/health/vault 九文件平铺），
   `ports.py` 单文件集中全部端口；「一业务域一模块」（conventions/04）只落到了
   server 路由与 web 分包，core 本身没有业务边界。
2. **反复推倒重建的主战场在 UI/品牌/文档层**：三天内三次方向调整、两次更名；
   裁决未回收到 spec（文档漂移），每次迭代像从零开始。
3. 逻辑层本身干净可用（无死代码、无超限文件、测试在），问题在组织方式与事实源治理。

用户六问逐项裁决：①core 按业务域分包（目录即业务）；②业务域 = accounts /
execution / usage / health / scheduling 五域 + shared 内核；③品牌、包名、仓库名
全面换 Butler（延续 ADR-011 映射总表）；④core+engine **从零重写**；
⑤connectors 六包搬家适配、apps 壳层只改 import 与包名；⑥**并入 ADR-010
多账号模型**一步到位，避免下一轮重构。

## 决策

1. **目录即业务**：`butler_core` 内按业务域分包——`shared / accounts / execution /
   usage / health / scheduling`，每域固定三件套 `domain.py + ports.py + usecases/`；
   端口随域走，不再全库一个 ports.py。`butler_engine` 对齐同一域图。
2. **依赖规则**：域间依赖只允许 `域 → shared`，禁止域互依；跨域编排由用例组合完成
   （用例可以跨域读，域的 domain.py 不得 import 其他域）。
3. **从零重写 core+engine**，行为语义与协议七字面量不变；connectors 六包搬家适配
   （manifest / 声明式数据不动）；apps 壳层只改 import 与包名。
4. **多账号并入**（ADR-010 全部五点落地）：Account 从应用单例变为集合，
   身份 = `(provider, account_key)`（`account_key` 缺省 `"main"` 兼容存量数据）；
   target 编址 = 应用 + 账号；幂等键 = `(kind, account_id, 窗口)`；凭据/权益/会话/
   用量全部按账号隔离；OpenAPI 契约再生成（红线 4）。
5. **历史包袱不带入**：`marina.vault` 读穿（改为装配期一次性迁移）、方言映射
   仅保留 ADR-002 纯数据字典、ProvisionRequest
   透传三处兼容层不由新代码继承，由**一次性数据迁移脚本**收口（迁移幂等、
   旧文件保留不删、写审计，机制承袭 A1-03 §7）。
6. **文档换代先行**（P0）：specs 按业务域重组（一域一册 A2-11..A2-15），
   过时表述全部回收；并在 conventions/02 增补第 8 条红线——
   **任何 ADR 合入时必须同步回收受影响 spec**，根治文档漂移。

实施分阶段（P0 文档 → P1 shared+accounts → P2 execution+scheduling →
P3 usage+health → P4 engine+数据迁移 → P5 connectors 适配+契约再生成 →
P6 apps 壳+web 多账号维度），每阶段验收 = 测试全绿 + 门禁九项全绿。
细则与验收标准见 [A1-05](../specs/architecture/A1-05-按业务域重写总设计.md)。

## 后果

**正面**：

- 目录即业务地图：新人/AI 进场看目录就知道业务边界，不再依赖口口相传
- 多账号一步到位，消除下一次"为多账号再推倒"的循环
- 端口随域走后，改动一个域的对外面只触碰该域的 ports.py
- 裁决回收入红线后，spec 与代码漂移有制度性拦截

**负面/约束**：

- 从零重写回归风险最大 → 以既有测试（迁移后全绿）+ 协议字面量不变 + 契约
  显式再生成三重兜底；每阶段门禁不得跳过
- 契约再生成波及 web/MCP（accounts 端点带账号维度）→ 集中在 P6，期间
  旧契约不再作为验收基准
- 远端仓库改名（`ai-kabao` → `ai-butler`）仍需用户在 Gitee 网页手工执行
  （ADR-011 批5 既定步骤，非本次新增）
