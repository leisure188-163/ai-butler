# ADR-015 · 登录态失效必须可见、可修，并停止自动重试

- **状态**：Accepted
- **日期**：2026-11-16
- **决策者**：butler 维护者
- **关联**：A2-02 §4（声明式鉴权码）、A2-07 §5（健康分级与修复）、
  A2-08 §2（调度闸门）、A4-01 §2/§3（严重度与通知渠道）、
  A3-01 §3（待办修复入口）、ADR-007 决策 8（会话级切号自动化；登录不自动化）

## 背景

qoder 真机签到返回 `HTTP 401`，但被记成 `FAILED`，形成一条完整的静默链：

1. **归类断线**：声明式运行时把传输层错误一律归 `FAILED`；
2. **可见断线**：`FAILED` 的 `is_attention=False`，`/pending` 只聚合 attention
   结果，仪表盘待办永远看不到它；
3. **可修断线**：传输错误分支不带 `repair_hint`，用户即使看到也不知道怎么修；
4. **重复断线**：`CheckinSchedule` 没有健康闸门，每个班次照打，上游持续 401。

用户感知是"一直在失败，也不知道什么情况"，而系统侧没有任何一处主动说
"这是登录态失效，需要你重新登录"。

候选方案中曾考虑"登录态失效后自动清空会话数据、强制客户端重新登录"，**否决**：

- 桌面四家（trae/qoder/workbuddy/doubao）的登录态在**客户端自己的存储**里，
  butler 清自己的库既不能强制客户端登出，也不能触发重登，只会丢掉证据与历史；
- 网页两家（chatgpt_web/claude_web）的 cookie 副本可以"失效即作废"，但它必须
  是**用户显式修复动作的一部分**，不能由调度器在后台静默清库；
- 登录本身按 ADR-007 决策 8 **不自动化**（扫码/手机号需人工参与）；账户间会话
  切换已自动化（决策 8，2026-11-17），但**登录态失效后的重登仍人工**——切号
  只能在已登录会话间进行，救不了过期会话。

## 决策

**选定四段闭环：归类 → 可见 → 可修 → 熔断。**

1. **归类**（A2-02 §4）：
   - `TransportError` 携带 `status_code`（仅 HTTP 非 2xx）；
   - `AuthSpec.reauth_status_codes` 由连接器显式申报，默认空 = 不申报；
   - 命中申报码 → `NO_AUTH` + 证据「鉴权被拒（HTTP xxx）——登录态已失效」+
     `RepairHint(action_id="relogin")`；未申报的 4xx/5xx 仍 `FAILED`，
     不替连接器猜 HTTP 语义；
   - trae_cn / qoder_cn 申报 `[401, 403]`。
2. **可见**（A2-07 §5、A4-01 §2/§3）：
   - `expired` / `invalid` 的严重度由 `BADGE` 升为 `PUSH`；`risk` 保持 `PUSH`；
   - 每次动作落地（`POST /runs`、`claim-all`、调度触发）后立即评估健康，
     级别变化发 `ACCOUNT_HEALTH_CHANGED`；
   - 新增系统通知渠道 `SystemChannel`（min_severity=PUSH）：macOS 用
     `osascript`、Linux 有 `notify-send` 则用；其它平台**如实抛错**，由通知中心
     隔离记日志，不假装送达；
   - server 默认开启（`BUTLER_SYSTEM_NOTIFY=1`），测试/CLI/引擎库默认关闭。
3. **可修**（A3-01 §3）：
   - `/pending` 原样带出 `repair_reason` 与 `repair_action_id`；
   - 待办行给「重新登录 / 重新扫描」入口；展开后是两步人工引导：
     「1. 打开客户端完成登录 → 2. 点『我已登录，立即重试』」；
   - 重试复用 `POST /runs`（带 `account_id`），按真实结果如实转述成败。
4. **熔断**（A2-08 §2）：
   - `CheckinSchedule` 注入 `assess_health`；触发前若级别为
     `invalid` / `expired` / `risk` 则跳过，不再按班次反复打上游；
   - 同一 `(target, account, window)` 只记一条 info 日志，不刷屏；
   - **手动重试不受闸门限制**（用户修完后必须能立刻恢复），成功后健康评估
     回到 `healthy`，下一班次自动恢复。

明确排除：

- 不做"登录态失效自动清空**客户端**会话数据 / 强制登出"（理由见背景）；
  butler 自己的本地副本撤销按 [ADR-016](ADR-016-失效凭据只撤销管家本地副本.md)
  执行——只清库、不动客户端；
- 不做自动登录（ADR-007 决策 8；会话级切号已自动化，但过期会话的重登仍人工）；
- 本期未实现 Windows toast：`SystemChannel` 在 Windows 显式失败并记日志，
  桌面壳接入时替换 runner（不是静默降级）。

## 后果

**正面**：

- 登录态失效从"静默失败"变成"待办里的一条 + 一次系统通知 + 一个重试按钮"；
- 失效账户不再消耗每个班次的无效请求，日志只留一条原因；
- 归类、严重度、通知、熔断各自单点可测（连接器/引擎/server 三层新用例覆盖）。

**负面/约束**：

- 失效判定依赖连接器**显式申报**鉴权码；新接入应用漏申报就仍会记 `FAILED`
  （这是有意的显式契约，需在接入清单里检查）；
- 健康事件只在级别**变化**时发：用户忽略首条通知后不会反复弹窗，但待办仍在；
- 修复的最后一步（在客户端重新登录）必须由用户完成，butler 无法代劳；
- 系统通知依赖平台命令（macOS `osascript` / Linux `notify-send`），无命令的
  headless 环境只留日志与应用内待办。
